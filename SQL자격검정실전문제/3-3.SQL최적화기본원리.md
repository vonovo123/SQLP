131. 실행계획에 대한 설명으로 가장 부적절한 것.

=> 실행계획이 달라도 결과는 달라지지 않는다.
d. 비용기반옵티마이저의 실행계획에는 단계별 예상비용 및 건수 등이 표시된다.

132. SQL 처리흐름도에 대한 설명으로 가장적절한 것

a. SQL 실행 시간을 알 수 있다.

b. 인덱스 스캔, 테이블 전체 스캔등 같은 액세스 기법이 표현된다.
c. 실행계획과는 무관한다.
=> SQL 처리 히름도는 실행게획을 시각화해서 표현한 것이다 실행시간을 알 수 없다.
d. SQL 내부적인 처리 절차를 시각적으로 표현해준다.

133. 옵티마이저와 실행계획에 대한 설명으로 부적절한 것

a.SQL처리흐름도는 성능적은 측면의 표현은 고려하지 않는다.
=> 인덱스 스캔 및 전체 테이블 스캔 등의 액세스 기법 표현은 물론, 성능적인 측면도 표현할 수 있다.

b.규칙기반옵티마이저에서 제일 높은 우선순위는 행에 대한 고유 주소를 사용하는 방법이다.
=> 규칙기반옵티마이저에서 제일 낮은 우선순위는 전체테이블스캔이고 제일 높은 우선순위는 ROWID를 활용한 테이블 액세스다.

c.SQL처리흐름도는 인덱스 스캔 및 전체 테이블 스캔 등의 액세스 기법을 표현할 수 있다.
=> 인덱스 스캔 및 전체 테이블 스캔 등의 액세스 기법 표현은 물론, 성능적인 측면도 표현할 수 있다.

d.인덱스 범위 스캔은 항상 여러 건의 결과가 반환된다.
=> 인덱스 범위 스캔은 결과 건수만큼 반환하지만, 결과가없다면 한건도 반환하지않을 수 있다.

134. 관계형 데이터베이스의 인덱스에 대한 설명으로 적절한 것.

a. 기본 인덱스에 중복된 키 값들이 나타날 수 있다.
=> 기본인덱스에는 UNIQUE & NOT NULL 제약조건이 있다.

b. 기본인덱스에 널 값이 나타날 수 없다.

c. 보조인덱스에 고유한 키 값들만 나타날 수 있따.
=> 보조인덱스는 UNIQUE 인덱스가 아니라면 중복 데이터의 입력이 가능하다.

d. 자주변경되는 속성은 인덱스를 정의할 좋은 후보다.
=> 자주 변경되는 속성을 인덱스로 선정할 경우 DML 성능이 저하될 가능성이 높다.

135. 관계형 데이터베이스의 인덱스에 대한 설명으로 부적절한 것.

a. 테이블의 전체 데이터를 읽는 경우 인덱스가 거의 불필요하다.
b. 인덱스는 조회 삽입 삭제 갱신 연산의 속도를 향상시킨다.
=> 조회만을 위한 오브젝트로 삽입 삭제 갱신의 경우 오히려 부하가 증가한다.
c. B트리는 관겨형 데이터베이스의 주요 인덱스 구조다.
d. 대량의 데이터를 삽입할 때는 모든 인덱스를 생성하고 데이터를 입력하는 것이 좋다.
=> 인덱스가 존재하는 상황에서 데이터를 입력하면 매번 인덱스 정렬이 일어나므로 데이터 마이그레이션 같이 대량 데이터를 삽입할때는 제거하고 끝난후 다시생성하는것이 좋다.

136. 인덱스에 대한 설명

B-Tree 인덱스는 브랜치 블록과 리프 블록으로 구성되며, 브랜치 블록은 분기를 목적으로하고 리프블록은 인덱스를 구성하는 컬럼의 값으로 정렬된다. 일반적으로 OLTP 시스템 환경에서 사용된다.

CLUSTERED 인덱스는 인덱스의 리프 페이지가 곧 데이터 페이지이며, 리프 페이지의 모든 데이터는 인덱스 키 컬럼 순으로 물리적으로 정렬되어 저장된다.

BITMAP 인덱스는 시스템에서 사용될 질의를 시스템 구현 시에 모두 알 수 없는 경우인 DW 및 AD-HOC 질의 환경을 위해 설게됐다.

하나의 인덱스 키 엔트리가 많은 행에 대한 포인터를 저장하고 있는 구조이다.

137. 인덱스에 대한 설명으로 가장 적절한것.

a. 인덱스는 인덱스 구성 칼럼으로 항상 오름차순으로 정렬된다.
=> 인덱스를 생성할 때 정렬 순서를 내림차순으로 하면 내림차순으로 정렬한다.
b. 비용기반 옵티마이저는 인덱스 스캔이 항상 유리하고 판단한다.
=> 비용계산을 통해 전체 테이블 스캔이 유리하다고 판단할 수있다.
c. 규칙기반옵티마이저는 적절한 인덱스가 존재하면 항상 인덱스를 사용한다.
d. 인덱스 범위 스캔은 결과가 없으면 한 건도 반환하지 않을 수 있다.

138. 인덱스에 대한 설명으로 적절한 것

```sql
CREATE INDEX IDX_EMP_01 ON EMP (REGIST_DATE,DEPTNO);

SELECT *
FROM EMP
WHERE DEPTNO = 47
AND REGIST_DATE BETWEEN '2015.02.01' AND '2015.02.28'
```

a. 실행된 SQL에 대해 인덱스 비효율이 있어 컬럼을 DEPTNO + REGIST_DATE 순으로 변경할 필요가 있다.
b. IDX_EMP_01 인덱스를 이용해 DEPTNO = 47 조건을 효율적으로 탐색할 수 있다.
=> REGIST_DATE 조건이 범위조건이고 DEPTNO 컬럼은 후행컬럼이므로 효율적으로 탐색할 수 없다.
c. REGIST_DATE 컬럼에 대한 조건을 범위 검색이 아닌 동등 검색 조건으로 변경하면 IDX_EMP_01를 효율적으로 활용할 수 있다.
d. IDX_EMP_01 인덱스는 테이블 내의 대량 데이터를 탐색할때 유용하다.
=> B\*Tree index는 일반적으로 테이블 내의 데이터 중 10%이하의 데이터를 검색할때 사용한다.

139. 인덱스에 대한 설명으로 부적절한것

a.인덱스의 목적은 조회 성능 최적화이다.
b.insert, update, delete 등의 dml 처리 성능을 저하시킬 수 있따.
c. b-tree 인덱스는 일치 및 범위 검색에 적절한 구조다.
d. 인덱스 액세스는 테이블 전체 스캔보다 항상 유리하다.
=> 인덱스를 스캔하여 테이블로 데이터를 찾아가는 방식이 랜덤 엑세스인데, 랜덤 엑세스의 비용이 크기 때문에 매우 많은 양의 데이터를 읽을 경우 인덱스 스캔보다 테이블 전체 스켄이 효율적일 수 있다.

140. 인덱스에 대한 설명으로 올바른 것.

a. 인덱스는 데이터 조회 목적에 효과적이지만, 그외 DML에 부하를 줄 수 있다.
b. 인덱스를 이용한 데이터 조회는 항상 테이블 전체 스캔보다 빠르다.
c. SQL SERVER의 클러스터형 인덱스는 오라클의 IOT와 매우 유사하다.
d. 인덱스는 UPDATE 작업시에는 부하가 없을 수도 있다.
=> 인덱스 구성에 포함되지 않는 컬럼에 대한 update는 부하가 없을 수 있다.
e. 인덱스를 활용해 데이터를조회할 때 인덱슬르 구성하는 컬럼 순서는 SQL 실행성능에 관계가 없다.

141. 옵티마이저의 실행계획에 대한 설명으로 옳은 것은

a. ORACLE의 규칙기반 옵티마이저에서 가장 우선순위가 높은 것은 single row by rowid 엑세스 기법이다.
b. 비용기반 옵티마이저는 테이블, 인덱스, 컬럼 등 객체의 통계정보를 사용하여 실행계획을 수립하므로 통계정보가 변경되면 실행계획이 달라질 수 있다.
c. ORACLE의 실행계획에 나타나는 기본적인 Join 방법으로는 NL, hash, Sort merge 조인이 있다.
d. 다양한 join 기법 중 NL join은 DW 등에서 데이터를 집계하는 업무에 많이 사용된다.
=> NL 조인은 데이터를 집계하는 업무 보다는 OLTP의 목록처리업무에 많이 사용된다. DW 집계업무에 많이 사용되는 JOIN 기법은 HASH, SORT MERGE join이다.

142. NESTED LOOP JOIN에 대한 설명으로 부적절한 것.

a. 조인 컬럼에 적당한 인덱스가 있어서 자연조인이 효율적일 때 유용한다.
b. Driving 테이블의 조인 데이터 양이 큰 영향을 준다.
c. 소트머지조인을 하기에는 두 테이블이 너무 커서 소트부하가 심할 때 유용하다.
=> 소트머지조인을 하기에 두 테이블이 너무 커서 부담스러울 때는 HASH JOIN을 사용한다.
d. 유니크 인덱스를 활용하여 수행시간이 적게 걸리는 소량 테이블을 온라인 조회하는 경우 유용하다.

143. SQL에 적절한 join 기법

```sql
-- PK_DEPT : DEPTNO
-- PK_EMP : EMPNO
-- IDX_EMP_01 : DEPTNO

SELECT *
FROM DEPT D
WHERE  D.DPETNO = 'A001'
AND EXISTS (SELECT 'X' FROM EMP E WHERE D.DEPTNO = E.DEPTNO)

```

EXISTS 절은 실행계획상 주로 SEMI JOIN으로 나타난다.
HASH SEMI, NL SEMI 모두 가능하지만 outer table이 조인 대상이 DEPT.DEPTNO = 'A001' 로 극도로 적기 때문에 nl semi join이 더 유리하다.

144. Sort merge join에 대한 설명으로 부적절한 것

a. 조인 컬럼에 적당한 인덱스가 없어서 nl 조인이 비효율적일때 사용할 수 있다.
b. Driving table의 개념이 중요하지 않는 조인 방식이다.
c. 조인 조건의 인덱스의 유무에 영향 받지 않는다.
d. equi 조인 조건에만 ㅈ동작한다.
=> Non-equi join 조건에서도 사용할 수 있다.

145. 해싱기법을 이용해 조인을 하는 해시조인은 한쪽 테이블이 주 메모리의 가용 메모리에 담길정도로 충분히 작고 해시 키 속성에 중복 값이 적을때 효과적이다.
     해시조인이 더 효과적일 수 있는 조건에 대한 설명으로 부적절한 것은

a. 조인컬럼에 적당한 인덱스가 없어서 자연 조인이 비효율적일때
b. 자연조인시 드라이빙 집합 쪽으로 조인 엑세스 량이 많아 RANDOM ACCESS 부하가 심할때

d. 유니크 인덱스를 활용해 수행시간이 적게 걸리는 소량 테이블을 온라인 조회하는경우
=> 유니크 인덱스를 활용하여 수행시간이 적게 걸리는 소량 테이블을 조인할 때는 NL 조인이 적합하다.

146. join 기법에 대한 설명으로 적절한 것은.

a. NL 조인은 선택도가 낮은 테이블이 선행 테이블로 선택되는것이 일반적으로 유리하다.
b. Sort merge join은 동등 join에서만 사용할 수 있다.
=> 비 동등 조인에서도 사용할 수 있다.
c. Hash join은 결과 행의 수가 큰 테이블을 선행 테이블로 사용하는 것이 성능에 유리하다.
=> 행의 수가 작은 테이블은 선행 테이블로 선택하는 것이 유리하다.
d. Hash join은 Sort merge join 보다 항상 우수한 성능을 보장한다.
=> join 대상 테이블이 Join key 컬럼으로 정렬되 있다면 sort merge join이 더 우수한 성능을 낼 수 있다
