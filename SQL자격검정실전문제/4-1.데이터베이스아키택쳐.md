1. 데이터베이스 연결에 관한 설명으로 부적절한 것.

a. 데이터베이스 서버와 클라이언트 간 연결상태를 유지하면 서버 자원을 낭비하게 되므로 동시 사용자가 많은 OLTP 환경에선 SQL 수행을 마치자마자 연결을 닫는게 바람직하다.
=> 다중 사용자 환경에서 서버와 클라이언트의 연결상태를 지속하면 서버 자원을 낭비하게 된다. 그렇다고 sql을 수행할 때마다 연결요청을 반복하면 서버 프로세스(또는 쓰레드)의 생성과 해제도 반복되므로 성능에 좋지 않다.
따라서 Connection Pooling 기법이 필수적이다.

b. 연결 요청에 대한 부하는 쓰레드 기반 아키텍쳐보다 프로세스 기반 아키택처에서 더 심하게 발생한다.
=> 데이터베이스 연결 요청 시, 프로세스 기반은 무거운 프로세스 생성 및 전환 비용 때문에 스레드 기반보다 부하가 더 심하게 발생한다.

c. 전용서버 방식으로 오라클 데이터베이스에 접속하면 사용자가 데이터베이스 서버에 연결 요청을 할 때마다 서버 프로세스가 생성된다.
d. 공유 서버 방식으로 오라클 데이터베이스에 접속하면 사용자 프로세스는 서버 프로세스와 직접통신하지 않고 Dispatcher 프로세스를 거친다.

2. ORACLE이나 SQL Server 같은 데이터베이스의 저장 구조를 설명한 것으로 부적절한 것은

3. 데이터 변경 사항을 데이터 버퍼 캐시에만 기록했다가 시간간격을 두고 데이터 파일에 일괄 반영하려면 반드시 REDO 로그의 도움이 필요하다.
   그래야 DBMS에 문제가 발생하더라도 안전하게 복구할 수 있다. REDO 로그 메커니즘의 특징을 설명하는 용여중 아래의 설명과 관련된 것으로 적절한 것은

   "버퍼 캐시 블록을 갱신하기 전에 변경사항을 먼저 로그 버퍼에 기록해야하며, Dirty 버퍼를 디스크에 기록하기 전에 해당 로그 엔트리를 먼저 로그 파일에 기록해야한다."

a.write ahead logging
b.log force at commit
=> LOG FORCE AT COMMIT은 로그 버퍼를 주기적으로 로그파일에 기록하되 늦어도 커밋 시점에는 반드시 기록해야 함을 뜻한다.
c. fast commit
=> 사용자의 갱신내용이 메모리상의 버퍼블록에만 기록된 채 아직 디스크에 기록되지 않았지만 redo 로그를 믿고 빠르게 커밋을 완료하는 것을 말한다.
d. delayed block cleanout
=> 변경된 블록을 커밋 시점에 바로 cleanout(로우 Lock 정보해제, 커밋 정보 기록) 하지 않고 두었다가 나중에 해당 블록을 처음 읽는 세션에 의해 정리되도록 하는 것을 말한다.

9. 프로그램을 작성할 때의 문제점과 거리가 먼 것

```sql
create function get_count(p_table varchar2, p_column varchar2, p_value varchar2)
return number
is
   l_sql long;
   l_count number;
begin
   l_sql := 'select count(*) from ||' p_table;
   if p_column is not null and p_value is not null then
      l_sql := l_sql || 'where' || p_column || ' =:1';
      execute immediate l_sql
               into l_count
               using p_value;
else
      execute immediate l_sql into l_count;
   end if;

   return l_count;
end get_count;
```

a. 불필요한 하드파싱을 많이 일으킨다.
=>Dynamic SQL 방식으로 코딩했지만, 바인드 변수를 사용했으므로 불필요한 하드파싱을 많이 일으키지 않는다.

b. 테이블 통계정보를 활용하지 못한다.
=> 바인드변수를 사용하면 컬럼 히스토그램을 활용하지 못하지만, 레코드 건수, 컬럼 값의 종류, null 값 개수 등을 활용해 실행계획을 수립한다.
c. 인덱스 전략 수립이 어렵다.
d. 실행계획을 제어하기 어렵다.

11. 데이터베이스 Call에 대한 설명으로 부적젏한 것.

a. SELECT 문장을 수행할 땐 Execute, Parse, Fetch 순으로 Call이 발생한다.
=> Select 문장을 수행할때는 Parse = Execute - Fetch 순으로 Call이 발생한다.
b. Select 문장에선 대부분 I/O가 Fetch Call 단계에서 일어난다.
c. group by를 포함한 Select 문장에서 group by 결과집합을 만들기까지 I/O는 Execute Call 단계에서, 이후 결과집합을 전송할 때의 I/O는 Fetch Call 단계에서 일어난다.
=> group by 결과집합을 만드는 과정에서의 I/O는 첫 번째 Fetch CAll에서 일어난다.
d. Insert, Update, Delete 문장에선 Fetch Call이 전혀 발생하지 않는다.

```sql

--          count  disk  query current rows

-- execute. 1000     0     0     0        0
-- fetch    5000     0   200000  0     500000
-- misses in library cache during parse : 1

-- query = consistent gets	= 일관성 읽기 (Logical Read). 버퍼 캐시에서 블록을 읽어온 횟수
-- current = db block gets = 	현재 블록 읽기 (Logical Read). 현재 블록 읽기(Current Read). 최신 버전 블록 그대로 읽기. 주로 DML 시 사용되며, 변경 가능(수정 목적)한 블록을 읽을 때 발생
-- disk = physical reads	디스크에서 실제 블록을 읽어온 횟수 (캐시에 없어서 디스크 I/O 발생)
```

=> 제시된 Call statistics 만으로는 ORder by 또는 Group by 연산의 포함여부를 판단할 수 없다.
c. 실행할때마다 평균적으로 200개의 블록을 읽었고, 필요한 블록을 모두 버퍼캐시에서 찾았다.
=> (query + current) / execute count
d. 매번 실행할 때마다 비슷한 양의 결과집합을 반환했다면 Array Size는 100 정도로 설정한 상태로 볼 수 있다.
=> Array size = rows / fetch count

16. 두 SQL의 성능비교

```sql
--가
select 고객명
from 고객
where 가입일자 = To_char(sysdate, 'yyyymmdd')
order by 고객명

--나
select *
from 고객
where 가입일자 = To_char(sysdate, 'yyyymmdd')
order by 고객명
```

[가입일자 + 고객명] 을 선두로 갖는 인덱스를 사용하면 가보다 나 sql의 블록 I/O 더 많이 발생한다.

---

가의 경우 인덱스만 읽고 처리를 완료할 수 있어 블록 I/O가 더 적게 발생한다.

가입일자만으로 구성된 단일 컬럼을 사용하면 두 sql 모두 테이블 액세스가 발생하므로 블로I/O는 똑같다.

가는 소트 공간에 고객명만 저장하지만, 나는 모든 컬럼을 저장해야하므로 더 많은 소트 공간을 사용한다.

나는 sql을 수행하면 조건절을 만족하는 모든 컬럼을 클라이언트에게 전송해야하므로 더 많은 트래픽이 발생한다.

c. 옵티마이저 행동에 영향을 미치는 가장 중요한 요소는 통계정보이므로 변경이 거의 없는 테이블이라도 통계정보를 매일 수집한다.
=> 변경이 거의 없는 테이블까지 매일 통계정보를 수집할 필요는 없다.
d. 필요하다면, 옵티마이저 힌트를 사용해 최적 액세스 경로로 유도한다.

18. 블록 I/O에 대한 설명으로 가장 부적절한 것은

a. Random I/O는 인덱스를 통해 테이블에 액세스할 때 주로 발생한다.
b. Direct Path I/O는 병렬로 인덱스를 통해 테이블을 액세스할 때 주로 발생한다.
=> 병렬로 TABLE FULL SCAN 할때 주로 발생
c. Single Block I/O는 인덱스를 통해 테이블에 액세스할 때 주로 발생한다.
d. Multiblock I/O는 인덱스를 이용하지 않고 테이블 전체를 스캔할 때 주로발생한다.

19. 데이터베이스 I/O 원리에 대한 부적절한 설명.

a. 한 쿼리 내에서 같은 블록을 반복적으로 액세스하면 버퍼 캐시 히트율은 높아진다.
b. multoblick I/O 는 한번의 I/O Call로 여러 데이터 블록을 읽어 메모리에 적재하는 방식이다.
c. 테이블 full scan할 때, 테이블이 작은 Extent로 구성되 앴을수록 더 많은 I/O Call이 발생한다.
d. 인덱스를 통해 테이블을 액세스할 때, 테이블이 큰 Extent로 구성되잇으면 더 적은 I/O Call이 발생한다.

---

Multiblock I/O 방식으로 읽더라도 Extent 범위를 넘어서까지 읽지는 않는다. 따랏 ㅓ작은 Extent로 구성된 테이블을 Full table scan 하면 i/O call이 더 많이 발생ㅎ나다.

반면, 인덱스를 통한 테이블 엑세스 시에는 single block I/O 방식을 사용하므로 extent의 크기가 call 횟수에 영향을 주지 않는다.

20. 다음 중 데이터베이스 I/O 원리에 대한 설명으로 가장 부적절한 것은?

a. 단 하나의 레코드를 읽더라도 해당 레코드가 속한 블록을 통째로 읽는다.
b. I/O를 수행할 때 익스텐트 내에 인접한 블록을 같이 읽는 것을 multoblock I/O라고 한다.
c. 테이블 블록을 scan 할 때는 Sequential I/O 방식을, 인덱스 블록을 스캔할 때는 Random I/O 방식을 사용한다.
d. Massively Parallel Processing 방식의 데이터베이스 제품에선 각 프로세스가 독립적인 메모리 공간을 사용하며, 데이터를 저장할 때도 각각의 디스크를 사용한다.
읽을 때도 동시에 각각의 디스크를 액세스하기 때문에 병렬 I/O 효과가 극대화된다.

---

SEQUENTIAL I/O 방식은 테이블이나 인덱스를 스캔할 때 사용한다. Random I/O 방식은 인덱스를 스캔하면서 테이블을 액세스할 때 사용한다.
