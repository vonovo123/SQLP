1. 월별지점매출 테이블을 읽어, 각 지점별로 판매월과 함께 증가하는 누적매출을 구하는 SQL

- 윈도우 함수를 이용한 방식으로 작성

```sql
select 지점, 판매월, 매출, sum(매출) over(partition by 지점 order by 판매월) 누적매출
from 월별지점매출

select 지점, 판매월, 매출, sum(매출) over (partition by 지점 order by 판매월 range between unbounded preceding and current row) 누적매출
from 월별지점매출
```

- 윈도우 함수나 스칼라 서브쿼리를 지원하지 않는 DBMS에서 활용할 수 있는 방식으로 작성(전체범위처리에 최적화된 방식으로 작성)

```sql
select t1.지점, t1.판매월, min(t1.매출), sum(t2.매출) 누적매출
from 월별지점매출 t1, 월별지점매출 t2
and t2.지점 = t1.지점
and t2.판매월 <= t1.판매월
group by t1.지점, t1.판매월
order by t1.지점, t1.판매월


select t1.지점, t1.판매월, t1.매출, sum(t2.매출) 누적매출
from 월별지점매출 t1, 월별지점매출 t2
and t2.지점 = t1.지점
and t2.판매월 <= t1.판매월
group by t1.지점, t1.판매월, t1.매출
order by t1.지점, t1.판매월
```

---

누적매출을 구할때는, 윈도우 함수를 지원하는 버전이라면 윈도우함수가 가정 효과적이고 성능도 빠르다.

윈도우 함수를 작성할때는 partition by 절ㅇ르 명확히 작성하는 것이 중요하다.

윈도우 함수를 지원하지않는 DBMS 버전이라면 부등호 조인을 이용해 누적매출을 구할 수 있다. 스칼라 서브 쿼리를 이용할 수도 있지만 전체범위처리에 효과적이지 못하다.

-- 주문테이블

```sql
and (c.거주지역코드, c.고객명) in(('02','김철수'), ('05','홍길동'))
```

-- sql1
select 주문번호, 업체번호, 주문일자, 주문금액,

  from 주문
  where 주문일자 like '201509%'

-- sql2-2
select 주문번호, 업체번호, 주문일자, 주문금액
from (
  select max(주문번호) over (partition by 업체번호 ) 마지막주문번호,
  주문번호, 업체번호, 주문일자, 주문금액

```

4. 최적 조회쿼리 작성

- 하루 주문 건수는 평균 2만건이며, 10년치 데이터가 저장돼 있다.
- 주문 데이터를 조회하는 화면은 고객번호는 입력하지 않을 수 있지만, 주문일자는 항상 입력해야한다.

- 최적의 인덱스 구성안을 제시해야한다.

-- 주문
-- Column name  is_pk Nullable  Data Type

and  주문일시 <  to_date(:ord_dt1, 'yyyymmdd') + 1

where 고객번호 = decode(:cust_no, null, 고객번호, :cust_no)
and  주문일시 >= to_date(:ord_dt1, 'yyyymmdd')
and  주문일시 <  to_date(:ord_dt1, 'yyyymmdd') + 1
order by 주문일시 desc

select 고객번호, 주문일시, 주문금액, 우편번호, 배송지

where 고객번호 is not null
and 고객번호 = :cust_no
and  주문일시 >= to_date(:ord_dt1, 'yyyymmdd')
and  주문일시 <  to_date(:ord_dt1, 'yyyymmdd') + 1
union all
select 고객번호, 주문일시, 주문금액, 우편번호, 배송지

and  주문일시 >= to_date(:ord_dt1, 'yyyymmdd')
and  주문일시 <  to_date(:ord_dt1, 'yyyymmdd') + 1
order by 주문일시 desc

-- X01 : 고객번호 + 주문일시
-- X02 : 주문일시ㄱ
```

5.페이징처리

고객상태코드 = 'AC'인 고객을 조회해서 등록일시, 고객번호 순으로 출력.

출려하고자하는 항목은 고객번호, 고객명, 등록일시, 연락처, 주소, 최근접속일자

최근접속일시는 최근 한 달 이내 마지막 접속일시를 의미, 접속이력이 없으면 Null 출력

한달 전 날짜를 구하는 함수는 trunc(add_months(sysdate, -1))

매번 20건씩 데이터를 읽어 그리드 화면에 추가하는 방식으로 페이징처리 구현.

파일로 출력버튼을 누르면 전체 조회 데이터를 파일로 일괄저장

두 요건에 대한 최적 SQL과 최적 인덱스 구성안작성

```sql
-- 고객
-- #고객번호
-- *고객명
-- *등록일시
-- *고객상태코드
-- 연락처
-- 주소

-- 고객접속이력
-- #접속일시
-- #고객번호
-- *접속경로

-- 요건
-- 1. 각 조회버튼에 대한 성능요건
-- 조회/다음 : 응답속도를 빠르게 튜닝하는 것이 중요
-- 파일로 출력 : 전체 처리속도와 시스템 리소스 사용량 최소화.
-- 2.화면 페이징 처리 요건
-- 조회/다음 버튼을 계속 눌러 뒤쪽 페이지로 많이 이동하는 경우가 간혹 있지만, 대개 3페이지 이내만 조회하고 멈추는업무
-- 페이지 마다 인덱스 스캔 지점을 찾기위해 union all 방식으로 복잡하게 구현하지 않아도 됨
-- 페이징방식으로 조회하는 동안 새로운 데이터가 등록되거나 기존 데이터가 삭제되는 경우는 고려하지 않음.
-- 향후 인덱스 구성이 변경되더라도 결과집합은 정확히 보장되야함
--- 3. view mergeing, jon predicate pushdown 등 쿼리변환은 작동하지 않으.
-- 인덱스 설계시, 성능에 도움안되는 컬럼을 추가하면 아됨
-- 병렬처리 불가

-- 데이터 분포 및 테이블 구성
-- 고객 테이블
-- 비파티션
-- 총고객수 = 10만명
-- 고객상태코드 'AC'인 고객수 2만명

-- 고객접속이력 테이블
-- 총 데이터 건수 : 1000만명
-- 접속일시 기준 월단위 파티션
-- 고객 접속이려PK는 Local Partitioned Index


-- 페이징처리용
-- 고객IDX : 고객상태코드 + 등록일시 + 고객번호
-- 고객접속이력IDX : 고객번호 + 접속일시
select  A.고객번호, A.고객명, A.등록일시, A.연락처, A.주소, (
  select max(접속일시)
  from 고객접속이력
  where 고객번호 = a.고객번호
  and  접속일시 >= trunc(add_months(sysdate, -1))
) 최근접속일시
from (
  select rownum as no, a.*
  from  (
    select 고객번호, 고객명, 등록일시, 연락처, 주소
    from 고객
    where  A.고객상태코드 = 'AC'
    order by A.등록일시, A.고객번호
  ) a
  where rownum <= :page * 20
) A
where no >= (:page -1) * 20 + 1



-- 파일출력용
select A.고객번호, A.고객명, A.등록일시, A.연락처, A.주소, B.최근접속일자
from 고객 A,
(
  select 고객번호, max(접속일시) 최근접속일시
  from 고객접속이력
  where 접속일시 >= trunc(add_months(sysdate, -1))
  group by 고객번호
) B
where  A.고객상태코드 = 'AC'
and A.고객번호 = B.고객번호(+)
order by A.등록일시, A.고객번호
```

---

- 회면 페이징 처리용 SQL을 정확히 작성해야한다.

온라인 화편 페이징 처리옹 SQL은 최초 응답속도 최적화 목표에 맞게 SQL을 작성해야한다.
인덱스를 이용해 부분범위처리가 가능하도록 구현한다.
일반적인 페이징처리 SQL의 단점은 앞 페이지에서 읽은 데이터를 다시 읽어야하므로 뒤 페이지로 이동할 수록 블록 I/O가 늘어난다는 점이다.
하지만 뒤쪽 페이지로 이동하는 경우가 흔치 않다는 요건이 있다면 가장 적합하다.
부분범위처리를 위해서는 Order by를 적합한 인덱스를 통한 인덱스 스캔으로 대체해야한다.

- 화면 페이징용 sql에서 최근접속일자는 맨 바깥쪽 select-list에서 스칼라 서브쿼리로 구현해야한다. 화면에 출력하는 20건에 대해서만 스칼라 서브쿼리르 수행하기 위함이다.

- 파일 출력용 sql은 정확하게 작성해야한다. 전체 데이터 출력용 sql은 전체 응답속도 최적화 목표에 맞게 sql을 작성해야한다.

- 고객인덱스는 정확히 설계해애한다.

파일 출력용 sql은 인덱스를 사용하면 오히려 비효율적이다. 따라서 인덱스는 화면 페이징 처리용 sql에 최적화되도록 설계해야한다.
고객테이블을 고객상태코드로 인덱스 range scan 하려면 선두 컬럼은 고객상태코드여야하고 부분범위처리가 가능하게하려면 order by 컬럼을 모두 추가해야한다.

- 고객접속이력 인덱스를 정확히 실계해애한다.

= 조건인 고객번호를 선두에 두고, 부등호 조건인 접속일지를 뒤쪽에 추가한다.

6.  주문, 배송, 고객 정보를 읽어 주문배송 테이블에 입력하는 야간 배치 프로그램을 튜닝한다.

대상 주문 데이터는 2016년 6월부터 8월까지 3개월

월별 주문건수는 1000만건, 월별 배송건수는 900만건

배송은 주문이 완료된 후 시작하고 고객수는 500만명

```sql
-- 고객
-- #고객번호
-- *고객명
-- *고객연락처
-- *등록일시

-- 주문
-- #주문번호
-- *주문일자
-- *주문고객번호
-- *주문상품수
-- *주문금액
-- *주문상태코드
-- 할인금액
-- 배송지주소코드
-- 배송지주소상세

-- 배송
-- *주문번호
-- *배송일자
-- 배송상태코드
-- 배송업체번호
-- 배송기사연락처

-- 파티션 규성
-- 주문: 주문일자 기순 월단위 Range 파티션
-- 배송 : 배송일자 기순 월단위 Range 파티션

-- 인덱스 구성
-- 주문
-- PK : 주문번호
-- N1 : 주문상태코드 + 주문일자 => local partition
-- N2 : 주문고객번호 + 주문일자 => local partition

-- 배송
-- PK : 배송번호
-- N1 : 주문번호 + 배송일자 => local partition
-- N2 : 배송일자 + 배송상태코드 => local partition

-- 고객
-- PK : 고객번호
-- N1 : 고객명 + 고객번호
```

아래 병렬 SQL과 예상실행계획을 분석해 가장 빠르게 수행할 수 있는 SQL 작성

```sql
-- 옵티마이저 힌트 변경이 필요하면 SQL문장에 정확히 기술
-- 야간 배치용 SQL이므로 다른 트랜잭션에 의한 동시 DMl 없음
-- 세션 파라미터 구성 변경이필요하면, 변경안 제시
-- 파티션 구성은 변경불가
-- 시스템 운영 정책상 허용된 최대 Parallel Degree = 4

insert into 주문배송 t
select /*+leading(o) use_nl(d) index(d) full(o), parallel(o*/
o.주문번호, o.주문일자, o.주문상품수, O.주문상태코드, o.주문고객번호
,(select 고객명 from 고객 where 고객번호 = o.주문고객번호)
from  주문 o. 배송 d
where o.주문일자 between '20160601' and '20150831'
and o.주문번호 = d.주문번호


-- INSERT STATEMENT
--    LOAD TABLE CONVENTINAL 주문배송
--      TABLE ACCESS BY INDEXROW ID 고객
--        INDEX UNIQUE SCAN 고객_Pk
--      PX COORDINATOR
--        PX SEND QC RANDOM :TQ10000
--          NESTED LOOPS
--            NESTED LOOPS
--              PX BLOCK ITERATOR
--                TABLE ACCESS FULL 주문
--              PARTITION RANGE ALL
--                INDEX RANGE SCAN 배송_N1
--              TABLE ACCESS BY LOCAL INDEX ROWID 배송
```

- 트랜잭션에 의한 동시 DML이 없는 야간 배치용 SQL이므로 병렬 DML 활요이 가능하다. 병렬로 Insert 하려면 우선 parallel DML을 활성화해야한다.

```sql
alter session enable parallel dml;
```

parallel DML을 활성화한 상태에서 insert 바로 뒤에 parallel 힌트를 추가하면 된다.

3천만건 정도면 Direct Path Load 기능만 활용해도 충분히 빠르게 insert 할 수 있다. Direct Path Load 기능을 사용하려면 insert 바로 뒤에 append 힌트를 추가하면 된다.

parallel insert는 따로 append 힌트를 사용하지 않아도 기본적으로 Direct Path Load 방식으로 작동한다.

- 인덱스를 이용한 Nl 조인은 소량 데이터를 조인하는데 적합하다.

수십만 건 이상 데이터를 조인할 때는 캐시히트률이 좋지 않는 한 결코 빠른 성능을 기대할 수 없다. 3천만건에 이르는 데이터를 조인하면서 캐시히트율이 좋을 수 없다.

따라서 주문, 배송을 Full Scan과 해시조인으로 유도해야한다.

주문 테이블은 주문일자 기준으로 월단위 Range 파티션된 상태이다. 다른 조건절 없이 파티션키인 주문일자 조건으로 3개월치를 조인하는데 인덱스를 사용할 필요는 없다.

- 배송테이블은 배송일자 기준으로 Range 파티션돼있다.

배송일자가 조건절에 없으므로 Full Scan으로 전체 파티션을 익어야한다. 그 결과 실행계획에 PARTITON RANGE ALL이 나타난다.

문제에서 '배송은 주문이 완료된 후 시작된다' 는 요건이 있으므로 이를 이용할 수 있다.

배송일자는 주문일자보다 항상 크고 주문일자는 20160601보다 항상 크다. 따라서 배송일자에 대한 날짜 비교 조건절을 넣을 수 있다.

이를 통해 전체 파티션을 읽지 않아도 된다.

설령 이 조건절을 추가하지 않아 전체 파티션을 읽더라도 인덱스를 이용한 NL 조인보다 FULL SCAN과 해시조인이 빠르다.

- 스칼라 서브쿼리는 NL 조인과 같은 방식으로 작동한다. 단 입력값과 결과값을 PGA에 캐싱한다는 점만 다르다.

하지만 고객수가 500만명이라면 스칼라 서브쿼리 캐싱이 도움되지않는다. 일반 조인문으로 변경 후 해시 조인으로 유도하는것이 낫다.

- 해시조인을 항상 Full scan으로 처맇애햐하는 것은 아니지만, 고객 테이블에는 조인 외에 다른 조건절이 없으므로 FUll scan 해야한다.

그리고 고객명과 고객번호만 읽으면 되는 상황이므로 테이블 전체를 스캔할 필요없이 고객\_N1 인덱스를 Fast full scan 하면된다.

- 야간배치용sql이고 대용량 데티러르 조인해야하므로 병렬처리를 적극활용해야한다.

고객 테이블은 인덱스만 읽도록 유도했으므로 병렬처리를 위해 parallel_index를 활용해야한다.

```sql
insert /*+parallel(t 4)*/ into 주문배송 t
select /*+leading(d) use_hash(o) use_hash(c) full(o) full(d) index_ffs(c) parallel(o 4) parallel(d 4) parallel_index(c 4)*/
o.주문번호, o.주문일자, o.주문상품수, O.주문상태코드, o.주문고객번호
from  주문 o. 배송 d, 고객 c
where o.주문일자 between '20160601' and '20150831'
and o.주문번호 = d.주문번호
and c.고객번호 = o.주문고객번호
and d.배송일자 >= '20160601'
```
